# 面试表达与项目亮点

## 1. 项目一句话介绍

「我做的是企业微信实施助手：基于 FastAPI + LangGraph + Qdrant 的知识问答系统，增强版加了可信回答、重复检测、反馈闭环、运营看板和多轮追问，形成可运营的知识闭环。」

## 2. 业务背景

实施群重复问题多、文档散、老人经验难传承。目标是让数字员工能答、能沉淀、能进化、能复盘。

## 3. 技术架构

FastAPI 接口 + Jinja2 后台；MySQL 存结构化数据；Qdrant 做向量检索；Redis 做短期会话；LangGraph 编排问答和沉淀；LangSmith 做链路观测。

## 4. 为什么用 LangGraph

问答不是一条直线：要校验输入、检索、判置信度、生成或降级、写日志、未命中还要 upsert。LangGraph 把步骤拆成节点，状态清晰，也方便企微和 API 共用不同 Graph 版本。

## 5. 为什么用 Qdrant

知识卡片多、问法多样，关键词匹配不够。Qdrant 做语义检索，配合相似度阈值和置信度分级，控制「什么时候强答、什么时候拒答」。

## 6. 为什么要做可信回答

RAG 最怕「看起来对其实胡编」。我们按 high/medium/low 分级：高分带出处，中分提示确认，低分直接说不确定并记未命中，避免误导实施同学。

## 7. 为什么要做重复检测

多人沉淀容易出现相似卡片，污染检索。沉淀路径加 DuplicateCheckService，打预警日志，审核时人工决定，不自动删库。

## 8. 为什么反馈不直接改知识

补充反馈质量参差不齐，直接改正式卡片风险大。MVP 只更新 useful/useless 计数，补充写 revision 建议，留给后续审核转正。

## 9. 为什么需要运营看板

没有看板只有 Demo 感。聚合 question_log、feedback、duplicate 等，看命中率、风险卡片、未命中 Top，才知道补哪块知识。

## 10. 为什么多轮追问采用 Redis

30 分钟 TTL 的最近一轮摘要足够覆盖「那在哪配置」类追问，比全量历史 prompt 轻、比 LLM 改写便宜稳定。Redis 挂了也能降级单轮。

## 11. 项目技术难点

- 置信度与可信展示策略和检索分数对齐
- 企微 CommandRouter 里反馈/沉淀/问答优先级
- 重复检测方案 A：预检不阻断、终检在 create_pending
- 看板多表聚合口径统一
- 规则追问不改写明确问题

## 12. 项目风险和边界

- 真实企微回调未接，主入口仍是 mock
- 多轮追问是规则改写，自然度不如 LLM
- revision 未做审核流
- 看板无缓存，数据量大要优化

## 13. 如果重构下一版怎么做

1. 接真实企微回调与卡片按钮
2. revision 审核通过后自动 merge + 向量更新
3. LLM 可选做追问改写
4. 看板预聚合 / Redis 缓存
5. 多租户权限与 HA 部署

## 14. 面试速记

- **LangGraph**：多步骤问答/沉淀编排
- **Qdrant**：语义检索 + 阈值控置信度
- **可信回答**：防幻觉、带来源
- **反馈闭环**：进化但不乱改库
- **运营看板**：可度量、可治理
- **Redis 追问**：轻量上下文，明确问题优先
