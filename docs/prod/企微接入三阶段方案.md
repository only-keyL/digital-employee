# 企微接入三阶段方案

## 阶段一：模拟企微输入消息，先走完项目主流程

### 阶段目标

先不配置企业微信后台，不处理公网 URL、不处理 HTTPS、不处理 Token 校验、不处理 EncodingAESKey 解密。

本阶段只做一件事：

```text
用模拟接口伪造“企微用户 @ 数字员工”的消息，
让它进入系统核心流程，
验证问答、RAG、沉淀、审核、日志、向量同步等业务链路是否完整。
```

也就是说，先证明项目本身能跑通，企微只是暂时被 mock 掉。

------

## 1.1 本阶段要实现什么

新增一个模拟企微消息入口：

```text
POST /api/mock/wecom/message
```

请求体示例：

```json
{
  "message_id": "mock_msg_001",
  "group_id": "test_group_001",
  "group_name": "实施测试群",
  "user_id": "zhangsan",
  "user_name": "张三",
  "content": "@数字员工 打印模板怎么配置？"
}
```

系统内部不要直接拿这个 JSON 到处传，而是转换成统一消息对象：

```python
MessageEvent
```

建议字段：

```text
channel          消息来源，例如 wecom_mock / wecom_tunnel / wecom_prod
message_id       消息唯一ID
group_id         群ID
group_name       群名称
user_id          用户ID
user_name        用户名称
content          用户原始消息
clean_content    去掉 @数字员工 后的真实问题
receive_time     接收时间
```

后续所有业务流程都只认 `MessageEvent`，不要直接依赖企微原始 XML。

------

## 1.2 本阶段核心流程

```text
模拟请求
  ↓
/api/mock/wecom/message
  ↓
构造 MessageEvent
  ↓
去掉 @数字员工
  ↓
判断是否为指令：
    - 沉淀
    - 取消沉淀
    - 模板
    - 普通问题
    - 知识卡片提交
  ↓
进入 LangGraph / RAG / 知识沉淀主流程
  ↓
写入 question_log / unanswered_question / knowledge_card
  ↓
返回模拟企微回复内容
```

------

## 1.3 本阶段重点验收内容

本阶段不验收“企微真实消息”，只验收系统核心能力。

### 问答链路验收

```text
用户输入普通问题
↓
系统检索 MySQL / Qdrant
↓
命中则返回答案
↓
未命中则记录 unanswered_question
↓
question_log 正常落库
```

### 沉淀模式验收

```text
用户输入：沉淀
↓
系统进入沉淀模式

用户输入：模板
↓
系统返回知识卡片模板

用户提交知识卡片
↓
AI 检查完整性
↓
MySQL + Qdrant 检查重复
↓
生成待审核 knowledge_card
```

### 审核链路验收

```text
管理员审核通过
↓
知识卡片状态变为 approved
↓
vector_status 变为 pending
↓
同步到 Qdrant
↓
后续问答可以检索到该知识
```

------

## 1.4 本阶段 Cursor 执行限制

给 Cursor 的要求应该明确写：

```text
本阶段禁止接入真实企业微信。
本阶段禁止配置企业微信后台 URL。
本阶段禁止实现复杂的企微加解密逻辑。
本阶段只允许新增 mock/wecom/message 模拟入口。
所有业务处理必须走统一 MessageEvent，不允许把 mock 请求体直接传入业务层。
```

------

## 1.5 本阶段完成标准

满足下面条件即可进入第二阶段：

```text
1. 本地可以通过 Postman / curl 模拟企微消息；
2. 普通问答流程可以跑通；
3. 沉淀、取消沉淀、模板三个指令可以跑通；
4. 用户提交知识卡片可以进入待审核；
5. 审核通过后可以同步向量库；
6. 问题日志、未命中日志、反馈日志正常记录；
7. 全流程不依赖真实企业微信。
```

# 阶段二：使用内网穿透，进行真实企微输入联调

## 阶段目标

本阶段开始接入真实企业微信后台，但项目仍然运行在你本地。

目标是：

```text
企业微信真实消息
  ↓
通过公网 HTTPS 穿透地址
  ↓
打到你本地 FastAPI 服务
  ↓
企微回调接口完成验签、解密、消息解析
  ↓
转换成 MessageEvent
  ↓
复用阶段一已经跑通的业务流程
```

这一步是“真实回调 + 本地服务”的联调阶段。

------

## 2.1 使用什么技术

推荐技术组合：

```text
本地服务：FastAPI + Uvicorn
内网穿透：cpolar / natapp / ngrok / frp / Cloudflare Tunnel
回调协议：企业微信 API 接收消息回调
消息格式：企业微信加密 XML
安全配置：Token + EncodingAESKey + msg_signature 校验
```

结合你是 Windows 本地开发，我建议优先级：

```text
第一选择：cpolar 或 natapp
第二选择：ngrok
第三选择：frp，需要你自己有公网服务器
第四选择：Cloudflare Tunnel，需要域名和 Cloudflare 配置
```

对你当前来说，**cpolar / natapp 最适合本地快速测试**。

------

## 2.2 本阶段前置条件

你需要准备：

```text
1. 本地项目可以正常启动；
2. /api/wecom/callback 接口已经实现；
3. 企业微信后台有自建应用；
4. 有管理员权限可以设置 API 接收；
5. 内网穿透工具可以生成 HTTPS 公网地址；
6. 项目 .env 已支持企微配置。
```

`.env` 中至少需要：

```env
WECOM_ENABLED=true
WECOM_CORP_ID=企业ID
WECOM_AGENT_ID=应用ID
WECOM_SECRET=应用Secret
WECOM_TOKEN=你自己填写的Token
WECOM_ENCODING_AES_KEY=企业微信后台生成的EncodingAESKey
WECOM_CALLBACK_URL=内网穿透生成的HTTPS地址/api/wecom/callback
WECOM_DEDUP_TTL_SECONDS=86400
```

------

## 2.3 本阶段需要实现的接口

真实企微回调接口：

```text
GET  /api/wecom/callback
POST /api/wecom/callback
```

### GET 用于企业微信 URL 校验

企业微信后台保存 URL 时，会请求：

```text
GET /api/wecom/callback?msg_signature=xxx&timestamp=xxx&nonce=xxx&echostr=xxx
```

你的接口要做：

```text
1. 读取 msg_signature、timestamp、nonce、echostr；
2. 使用 Token + EncodingAESKey 校验签名；
3. 解密 echostr；
4. 返回解密后的明文；
5. 企业微信校验通过后，后台才能保存配置。
```

### POST 用于接收真实消息

企业微信用户在群里 @ 数字员工后，会请求：

```text
POST /api/wecom/callback
```

你的接口要做：

```text
1. 读取 XML 请求体；
2. 校验 msg_signature；
3. 解密消息；
4. 解析企业微信消息内容；
5. 判断是否是文本消息；
6. 判断是否为 @数字员工；
7. 转换成 MessageEvent；
8. 调用阶段一已经实现的核心处理服务；
9. 返回 success 或加密后的响应。
```

## 2.4 具体操作步骤

### 第一步：启动本地项目

PowerShell 示例：

```powershell
cd F:\WorkSpace\digital-employee-assistant

.\.venv\Scripts\activate

uvicorn app.main:app --host 0.0.0.0 --port 8001
```

确认本地接口能访问：

```powershell
curl http://127.0.0.1:8001/health
```

------

### 第二步：启动内网穿透

假设使用 cpolar，目标是把本地 `8001` 暴露成公网 HTTPS。

示例：

```powershell
cpolar http 8001
```

它会生成一个类似这样的地址：

```text
https://abc123.cpolar.cn
```

那么企业微信回调 URL 就是：

```text
https://abc123.cpolar.cn/api/wecom/callback
```

如果使用 natapp，逻辑类似：

```text
natapp 映射本地 8001
↓
生成公网 HTTPS 地址
↓
企业微信后台填写该地址 + /api/wecom/callback
```

------

### 第三步：配置企业微信后台

进入企业微信后台：

```text
应用管理
  ↓
自建应用
  ↓
数字员工
  ↓
接收消息
  ↓
设置 API 接收
```

填写：

```text
URL:
https://abc123.cpolar.cn/api/wecom/callback

Token:
自己定义，例如 DigitalEmployeeTestToken2026

EncodingAESKey:
点击随机生成
```

注意：这里填写的 Token 和 EncodingAESKey 必须和项目 `.env` 完全一致。

------

### 第四步：保存并校验 URL

点击保存时，企业微信会立即访问：

```text
GET /api/wecom/callback
```

如果你的接口验签和解密正确，企业微信后台会提示保存成功。

如果失败，优先排查：

```text
1. 本地项目是否正在运行；
2. 内网穿透地址是否能访问；
3. URL 是否带了 /api/wecom/callback；
4. Token 是否一致；
5. EncodingAESKey 是否一致；
6. GET 校验逻辑是否正确返回 echostr 明文；
7. 企业微信是否要求备案域名，导致穿透域名无法保存。
```

------

### 第五步：在企微测试群中 @ 数字员工

测试群中输入：

```text
@数字员工 打印模板怎么配置？
```

预期链路：

```text
企业微信
  ↓
内网穿透 HTTPS 地址
  ↓
本地 FastAPI /api/wecom/callback
  ↓
解密 XML
  ↓
解析消息
  ↓
转换成 MessageEvent
  ↓
进入问答流程
  ↓
返回回复
```

------

## 2.5 本阶段重点注意事项

### 1. 内网穿透不是生产方案

内网穿透只用于开发测试，不要写成正式部署方案。

原因：

```text
1. 地址可能变化；
2. 稳定性不可控；
3. 性能不可控；
4. 安全性不适合生产；
5. 企业微信可能限制随机域名；
6. 可能无法满足备案主体要求。
```

------

### 2. 如果企业微信后台不接受穿透域名

你截图里已经出现过“备案主体”提示，所以存在这种风险。

如果保存 URL 失败，不一定是代码问题，也可能是：

```text
企业微信要求回调域名备案主体与企业主体一致
```

这时阶段二可以降级为：

```text
使用内网穿透测试接口可达性
但不强求企业微信后台保存成功
真实保存放到阶段三服务器域名完成
```

------

### 3. 真实企微消息要做去重

企业微信可能因为超时或网络问题重试推送。

所以 POST 接收时要做：

```text
message_id 去重
```

建议：

```text
Redis key:
wecom:message:dedup:{message_id}

TTL:
86400 秒
```

如果重复消息进来，直接返回 success，不重复调用大模型。

------

### 4. 回调接口必须快速响应

企业微信回调不适合长时间等待大模型生成。

建议处理方式：

```text
收到消息
  ↓
验签解密
  ↓
记录消息
  ↓
立即返回 success
  ↓
后台异步执行问答流程
  ↓
通过企业微信发送消息接口主动回复
```

不过在阶段二，为了简单联调，可以先同步处理，但要知道生产阶段应该异步化。

------

## 2.6 本阶段完成标准

满足下面条件即可进入第三阶段：

```text
1. 内网穿透地址可以访问本地 FastAPI；
2. 企业微信 GET URL 校验接口通过；
3. POST 能接收到真实企微推送；
4. 能解析出用户、群、消息内容；
5. 能转换成统一 MessageEvent；
6. 能复用阶段一核心问答/沉淀流程；
7. 能记录真实企微消息日志；
8. Redis 去重逻辑生效；
9. 已明确内网穿透存在的限制和风险。
```

# 阶段三：正式部署到服务器，进行线上测试

## 阶段目标

本阶段将项目部署到测试服务器或生产服务器，使用稳定的公网 HTTPS 域名接入企业微信。

目标是：

```text
正式企业微信应用
  ↓
公司 HTTPS 域名
  ↓
Nginx
  ↓
FastAPI 服务
  ↓
企微回调适配器
  ↓
统一 MessageEvent
  ↓
核心业务流程
  ↓
主动回复企微用户
```

这一步才是正式接入。

------

## 3.1 推荐技术架构

```text
服务器：公司测试服务器 / 云服务器
域名：公司已备案域名，例如 ai-test.company.com
HTTPS：Nginx + SSL 证书
应用服务：FastAPI + Uvicorn / Gunicorn
数据库：MySQL
缓存：Redis
向量库：Qdrant
大模型：DeepSeek / 其他在线模型
观测：LangSmith
进程管理：Docker Compose / systemd / Supervisor
```

推荐部署方式：

```text
Docker Compose
```

因为你的项目依赖比较多：

```text
FastAPI
MySQL
Redis
Qdrant
LangSmith
DeepSeek API
```

Docker Compose 更适合统一管理。

------

## 3.2 服务器部署步骤

需要运维或你自己准备：

```text
3. HTTPS 证书；
4. 开放 80 / 443 端口；
5. 安装 Docker、Docker Compose、Nginx。
```

```text
https://ai-test.company.com
```

正式回调 URL：

```text

```

### 第三步：配置 Nginx 反向代理

核心配置：

```nginx
server {
    listen 443 ssl;
    server_name ai-test.company.com;

    ssl_certificate     /etc/nginx/ssl/ai-test.company.com.crt;
    ssl_certificate_key /etc/nginx/ssl/ai-test.company.com.key;

    location / {
        proxy_pass http://127.0.0.1:8001;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

企业微信回调会访问：

```text
https://ai-test.company.com/api/wecom/callback
```

Nginx 转发到：

```text
http://127.0.0.1:8001/api/wecom/callback
```

# 三阶段整体关系

可以用这张流程理解：

```text
阶段一：模拟输入
Postman / 页面模拟
  ↓
MessageEvent
  ↓
核心业务流程

阶段二：内网穿透
企业微信真实消息
  ↓
穿透地址
  ↓
本地 /api/wecom/callback
  ↓
MessageEvent
  ↓
核心业务流程

阶段三：正式部署
企业微信真实消息
  ↓
公司正式 HTTPS 域名
  ↓
服务器 /api/wecom/callback
  ↓
MessageEvent
  ↓
核心业务流程
```

核心设计是：

```text
三阶段只改变“消息从哪里来”
不改变“消息进入系统后怎么处理”
```

# 最终建议放入开发计划的版本

你可以把企微接入拆成下面三个阶段：

