# 新人快速上手指南

> 适合刚接手项目、想先建立整体认知，再逐步看代码的同学。

## 1. 先用一句话理解这个项目

这是一个面向**企业微信实施群**的知识沉淀型数字员工 MVP。

它解决的不是“怎么做一个聊天机器人”，而是“怎么把实施群里重复出现的问题，逐步沉淀成可复用的知识库”。

核心闭环是：

```text
提问 -> 检索知识 -> 命中则回答 -> 未命中则沉淀 -> 人工审核成知识卡片 -> 同步向量库 -> 下次再命中
```

## 2. MVP 已经做到什么

当前 MVP 已经完成阶段一到阶段十一，能演示、能验收、能跑通完整闭环。

已交付的核心能力：

| 模块 | 已实现能力 |
|------|------------|
| 知识管理 | 知识卡片新增、编辑、审核、启停、逻辑删除、向量同步 |
| 智能问答 | `/api/ask`、`/ask-test`、Qdrant 检索、LLM 生成答案 |
| 流程编排 | LangGraph 8 节点工作流 |
| 未命中沉淀 | 未命中问题入池、AI 草稿预览、转知识卡片 |
| 反馈统计 | useful / useless / need_human、统计看板 |
| 可观测性 | LangSmith tracing，可选开启，默认关闭 |
| 企业微信 | Mock 回调可演示，真实回调接口已预留 |

## 3. MVP 没有做到什么

这个项目当前是 **Demo / MVP**，不是生产上线版本。

明确还没做完的部分：

| 领域 | 当前边界 |
|------|----------|
| 企业微信生产接入 | AES 完整加解密未完成，真实公网 HTTPS 部署未完成 |
| 高可用部署 | Qdrant 当前是 local 模式，适合本地演示，不是集群方案 |
| 安全 | 无完整脱敏、无统一鉴权、无完整审计体系 |
| 模型能力 | 无流式输出、无多模型路由、无复杂多轮对话 |
| 运维 | 无完善告警体系，LangSmith 默认关闭 |

你可以把它理解为：**业务思路和技术闭环已经验证成立，但生产化还没做。**

## 4. 业务流程怎么理解

最重要的是理解两条分支：**命中** 和 **未命中**。

### 4.1 命中分支

```text
用户提问
-> 系统检索知识库
-> 找到已审核、已启用、已同步向量库的知识卡片
-> 基于知识卡片生成答案
-> 返回答案
-> 记录 question_log
-> 用户可提交反馈
```

### 4.2 未命中分支

```text
用户提问
-> 系统检索知识库
-> 没找到可信答案
-> 返回保守提示
-> 记录 question_log
-> 写入 unanswered_question
-> 人工后续处理
-> 转为知识卡片 draft
-> 审核通过
-> 同步到 Qdrant
-> 下次类似问题可命中
```

一句话说，**未命中不是失败，而是知识库继续变好的入口。**

## 6. 技术架构怎么理解

这个项目不是前后端分离，而是比较典型的 **后端主导型 MVP**：

| 层级 | 技术 / 角色 |
|------|-------------|
| Web 层 | FastAPI + Jinja2 + Bootstrap 5 |
| 业务主库 | MySQL |
| 向量检索 | Qdrant local |
| Embedding | fastembed |
| 工作流编排 | LangGraph |
| LLM | MockLLM / DeepSeek |
| 可观测 | LangSmith |

如果你有 Java 背景，可以这样类比：

| 本项目 | Java 常见理解 |
|--------|---------------|
| `router` | Controller |
| `service` | Application Service / Domain Service |
| `repository` | DAO / Mapper |
| `AskState` | 流程上下文 DTO |
| LangGraph | 工作流 / 状态机 |
| Qdrant + RetrievalService | 搜索引擎 + 业务过滤 |

## 7. 最重要的代码主链路

### 7.1 Web 问答主链路

```text
POST /api/ask
-> app/routers/ask_router.py
-> app/services/ask_service.py
-> app/agent/graph_runner.py
-> app/agent/workflow.py
-> app/agent/nodes.py
-> app/services/retrieval_service.py
-> app/services/answer_generation_service.py 或 handle_miss
-> app/services/ask_log_service.py
```

### 7.2 企业微信 Mock 主链路

```text
POST /api/wecom/mock/callback
-> app/routers/wecom_router.py
-> app/services/wecom_callback_service.py

```

这点非常重要：**企业微信入口没有单独做第二套问答逻辑，而是复用了 `/api/ask` 的主链路。**

## 8. LangGraph 在这个项目里做了什么

LangGraph 负责把问答流程拆成一串清晰可维护的节点。

当前主流程是：

```text
validate_input
-> preprocess_question
-> retrieve
-> match_judge
-> generate_answer / handle_miss / error_fallback
-> write_log
```

每个节点的职责：

| 节点 | 作用 |
|------|------|
| `validate_input` | 校验空问题 |
| `preprocess_question` | 预处理问题，当前基本是占位 |
| `retrieve` | 检索 Qdrant + 回查 MySQL |
| `match_judge` | 判断是否命中 |
| `generate_answer` | 命中后生成答案 |
| `handle_miss` | 未命中时返回保守答案 |
| `error_fallback` | 检索异常时兜底 |
| `write_log` | 写入日志和未命中记录 |

## 9. RAG 在这个项目里怎么落地

这个项目的 RAG 不是“直接查向量库就完了”，而是分成两步：

```text
问题
-> Embedding
-> Qdrant 检索
-> MySQL 回查知识卡片状态
-> 判断是否达到阈值
-> 命中则进入答案生成
```

为什么还要回查 MySQL？

因为 Qdrant 里只负责“相似度检索”，但真正的业务主数据在 MySQL。

只有满足下面三个条件的卡片，才允许参与回答：

```text
deleted=0
audit_status=approved
enabled=1
```

## 10. 知识卡片为什么是这个项目的核心

这个项目表面上是问答，底层本质是“知识运营”。

知识卡片承担了三件事：

1. 作为回答依据。
2. 作为向量检索的内容来源。
3. 作为未命中问题沉淀后的最终承载物。

它的典型生命周期：

```text
draft -> pending -> approved / rejected
```

只有 `approved` 且 `enabled=1` 的卡片，才会进入向量库并参与问答。

## 14. 新人最容易卡住的几个点

### 14.1 这不是普通 FAQ 系统

它不是静态问答，而是一个“会把未命中问题继续沉淀成知识”的系统。

### 14.2 未命中不是 bug

未命中是业务闭环的一部分，系统会把它记录下来，供人工补知识。

### 14.3 LLM 不是这个系统的唯一核心

LLM 只负责“命中后的答案组织”，真正决定系统质量的是：

1. 知识卡片质量。
2. 检索命中质量。
3. 未命中沉淀闭环。

### 14.4 Qdrant local 有单实例限制

执行 `rebuild_qdrant.py --recreate` 前，必须先停掉 uvicorn。

## 15. 如果你只记住 5 句话

1. 这是一个“知识沉淀型数字员工”，不是单纯聊天机器人。
2. MVP 主闭环是“问答 -> 沉淀 -> 审核 -> 再问答”。
3. 问答主入口是 `AskService`，流程核心在 LangGraph。
4. 知识卡片是业务核心，Qdrant 只是检索工具，不是主数据源。
5. 当前已能演示和验收，但还不是生产上线方案。
